# The two stack shapes

Every platform in the estate (except the static marketing site) is built with an AI app
builder on one of two stacks. Knowing which shape a repo is tells you where checkout logic,
server functions and routing live before you open a single file.

## Shape A — Vite + React (the majority)

Most programme sites, the Application Portal, the Learner Portal, the Ops Tool and the Growth
Partner Portal are this shape.

```
index.html
src/
  App.tsx                 # react-router routes
  pages/                  # one component per route
  components/
    ui/                   # shadcn/ui primitives, lightly customised
    <feature>/
  integrations/
    supabase/client.ts     # auto-generated by the builder — do not hand-edit casually
    <platform>/client.ts   # hand-written override when the schema isn't the default public
  lib/                     # pure helpers, data access, formatting
  hooks/
supabase/
  config.toml              # project_id, per-function verify_jwt
  functions/
    _shared/                # cross-function helpers (db clients, pricing, auth guards)
    <name>/index.ts
  migrations/               # timestamped SQL files
tailwind.config.ts
vite.config.ts
components.json            # shadcn config
```

Package manager: **bun** almost everywhere (`bun.lock` or `bun.lockb`); a few repos also carry
a stray `package-lock.json` from an npm run during a security scan or CI step — harmless if
`.gitignore`d, a real latent bug if committed (see the `overrides`-vs-`dependencies` conflict
in the lessons document). Dev/build: `bun run dev`, `bun run build`, `bun run lint`,
`bun run test` (vitest), `bunx playwright test` where e2e exists.

Env var names used by the builder's generated client: `VITE_SUPABASE_URL`,
`VITE_SUPABASE_PUBLISHABLE_KEY` (or `_ANON_KEY`), `VITE_SUPABASE_PROJECT_ID`. A platform on the
own-project-auth split additionally sets non-`VITE_` server-only vars for its edge functions:
`EXT_SUPABASE_URL`, `EXT_SUPABASE_SERVICE_KEY` (names vary slightly per repo — always read the
actual `_shared/db.ts`-equivalent file rather than assume).

**One variant**: a platform with server-side rendering adds its own `vite.ssr.config.ts`
alongside the normal `vite.config.ts` — check for this file before assuming every Vite repo is
a pure client-rendered SPA.

## Shape B — TanStack Start (a growing minority)

The Pre-Law Platform, the Challenge Platform, Builders Lab and the Counselling CRM are this
shape; newer platforms increasingly start here.

```
src/
  routes/
    __root.tsx
    index.tsx
    apply.tsx
    _authenticated/        # route group requiring auth middleware
  lib/
    *.functions.ts          # createServerFn() server functions — the TanStack analogue
                             # of a Supabase edge function, but co-located with the frontend
    *.server.ts              # server-only helper modules imported only by *.functions.ts
    *.test.ts
  start.ts                  # global middleware (e.g. requireSupabaseAuth, attachAuth)
drizzle/                     # drizzle-orm schema + migrations, when the platform uses it
  (check whether it's actually wired to a live DB or just scaffolding before trusting it)
drizzle.config.ts
```

Checkout/pricing/promo logic on this shape lives in `src/lib/*.server.ts`, **not** in
`supabase/functions/` — there may be only a handful of edge functions left for things that
genuinely need to run outside the request/response cycle (webhooks, cron). Never port an
edge-function fix to this shape verbatim; re-implement it as a server function.

Package manager: bun. Test runner: vitest (`bun test` or `vitest`), occasionally
`bun-test-mock.d.ts` style shims for environment pieces the test runner can't reach.

## Cross-cutting

- `components.json` (shadcn) and a `tailwind.config.ts` exist in nearly every repo regardless
  of shape — the design-token document assumes this file exists and reads its `theme.extend`.
- `deno.json` appears only inside individual `supabase/functions/<name>/` directories that need
  an import map (rare; most functions use plain `https://esm.sh/...` imports with a pinned
  version and no import map at all).
- CRLF line endings are common on Windows-checked-out repos and will make a bulk `lint` run
  nearly 100% red on files nobody touched — see the verification-discipline playbook: lint only
  the files actually changed.
- A repo with both `bun.lock(b)` and `package-lock.json` should be treated as suspect: `bun`
  tolerates an `overrides`/`dependencies` version mismatch that `npm install` rejects outright
  with `EOVERRIDE` — a project that only ever builds locally with bun can carry this invisibly
  until something downstream (a hosting pipeline's default build step, or `npx` run from inside
  the directory) uses npm.
