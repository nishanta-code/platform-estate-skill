## 1. The business in one paragraph

the Group (Group) runs many programme brands for high-school students — university
mentor-led fellowships, debating championships, pre-med and pre-law academies, finance
literacy, Test-Prep Platform prep, research programmes, founder programmes, in-person camps and
conferences. Each brand has its own marketing site and its own Lovable project; students
apply and pay through a central Application Portal; paid students are enrolled into one
shared Learner Portal; sales staff run school outreach, meetings and follow-ups on an
internal lead-management platform; a research/outreach platform mines school contacts and
tracks campaign → application → revenue attribution. All of it sits on Supabase (Postgres +
Auth + Edge Functions + Realtime + Storage), is built with Lovable (Vite+React or TanStack
Start, Tailwind, shadcn/ui), and is version-controlled on GitHub under the
one GitHub organisation.

### 3.3 Brain — `<BRAIN_REF>`

Used by Research Outreach. Not visible to this account's Supabase MCP connector (permission denied); it has been administered with a short-lived personal access token through the Management API (`POST /v1/projects/<ref>/database/query`). Schemas: `brain_ops` (~170 tables: campaigns, recipients, links, NPF/Meritto jobs, Instantly webhook events, applications/enrollments/payment_events bridge, dedup tooling), `public` (research_schools/contacts/campaigns + `brain_api_*` RPCs), `revenue_brain`, `quarantine`, `brain`.

Access pattern (non-negotiable): RLS is enabled with **zero policies** on the research tables, so a signed-in user's direct `.from()` returns empty. Every read/write goes through `SECURITY DEFINER` RPCs named `public.brain_api_*` that derive the actor from `auth.uid()` and re-check `brain_ops.member_roles`. See `docs/01-supabase/brain-rpc-pattern.md`.

## 4. The money and data flows (big picture)

```
Marketing sites (Pre-Med Platform, Financial Literacy Platform, Fellowship Platform, Pre-Law Platform, Research Platform, Test-Prep Platform, Founders Platform, Purpose Platform, Challenge Platform, Builders Lab)
   │  lead capture (captured_leads / *_masterclass_regs / interest_signups)       ┐
   │  masterclass registration → email + WhatsApp confirmations                  │ each platform's
   │  /pay checkout (own) ── Stripe / Razorpay / Flywire ── webhook ──┐          │ own schema on
   │                                                                   │          │ the shared estate
   └── "Apply" CTA ──────────────► apply.example-group.com ─────────┤          ┘
                                   (Application Portal, portal)      │
                                   /apply/{pay_slug} form → applications
                                   /pay/{pay_slug} or /pay/{link_slug} → Stripe PaymentIntent
                                   promo_codes validated centrally; payment_links override price
                                                                       │
                                        public.stripe_payments / razorpay_payments ◄┘
                                                                       │
                     LMS enrollment engine (lms.enrollment_runs → lms.enrollments → login rollout)
                                                                       │
                     Learner Portal: sessions, attendance, community, vault credits, referrals, certificates
                                                                       │
          Ops Tool / Sales Command / Research & Outreach: schools → contacts → campaigns → meetings → deals → attribution
                                                                       │
                     Console (finance schema): program codes, Xero/Wallex/DBS reconciliation
```

Key contracts that hold it together (each has its own document):

- **Catalogue**: `public.all_partners → all_programs → all_cohorts`, `all_mentors`, `all_masterclasses`. Programme codes `CATEGORY-ORG-PROGRAM-DDMMYY[-SCHOOL]` minted only in Console. `pay_slug` is the master programme identifier driving `/apply/{pay_slug}` and `/pay/{pay_slug}`. → `docs/01-supabase/catalogue-program-codes-and-slugs.md`
- **Checkout**: server-computed amounts, `early_bird_price` wins when > 0 else `sticker_price`, promo codes validated against central `public.promo_codes`, payment links override price and disallow promos, `metadata.program_code` mandatory on every PaymentIntent, unattributed payments go to manual review. → `docs/01-supabase/payments-checkout-and-promo.md`
- **Identity**: one email = one account on the estate; no trigger on `auth.users`; each platform provisions its own profile row; registration goes through server-side edge functions with point lookup (`<schema>.auth_user_id_by_email`), rate limits, honeypots, neutral errors. → `docs/01-supabase/auth-and-identity.md`
- **Security posture**: RLS everywhere; `has_role` per schema (never `public.has_role()`); service-role only inside edge functions; `verify_jwt=false` + in-code auth; secrets in Supabase secrets/Vault, never in the repo. → `docs/01-supabase/rls-security-and-grants.md`
