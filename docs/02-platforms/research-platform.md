### 1.1 How the own-project-auth vs central-data split is wired

- **Browser → own project only.** `src/integrations/supabase/client.ts` is the autogenerated Lovable client (auth storage brokered to the Lovable editor on preview surfaces by `src/integrations/supabase/previewAuthStorage.ts`). The browser never holds central credentials. `src/integrations/supabase/types.ts` is empty of tables (the own project holds no business tables any more).
- **Browser → central = through one proxy.** `src/lib/centralDb.ts` wraps `supabase.functions.invoke("central-db", { body })` with typed actions: `catalog` (public), `public_read` (published_papers / all_masterclasses_public), `submit_application` / `submit_masterclass` (public), `track_event` (public analytics), `teacher_public` (email-gated teacher kit), `me` / `profile_update` / `role_self_add` / `my_role_row` (signed-in account), `select` / `query` / `update` / `insert` / `insert_many` / `upsert` / `delete` / `create_invite` (staff/admin).
- **Edge functions → central.** `supabase/functions/_shared/central.ts` exports `centralClient()` (schema `research`) and `centralPublicClient()` (schema `public`, used for `all_masterclasses` join links/passcodes that are deliberately absent from the `research` views). `_shared/checkout.ts` has its own `centralPublicClient()` for the catalogue; `_shared/paymentLinks.ts` builds a client pinned to schema `portal` for `get_public_payment_link`.
- **Roles live centrally.** `central-db` verifies the caller's JWT with the LOCAL service role (`local().auth.getUser`) then reads `research.user_roles` for roles (`callerIdentity()`); `_shared/requireTeacher.ts` and `_shared/requireTeacherOrCron.ts` do the same for admin-only functions. Roles: `admin`, `teacher`, `mentor`, `school`, `student` (`src/hooks/useUserRole.tsx`); only `student` may be self-added (`role_self_add`).
- **Env/secret NAMES used by functions** (from `Deno.env.get` scan): `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, `SUPABASE_ANON_KEY`, `EXT_SUPABASE_URL`, `EXT_SUPABASE_SERVICE_KEY`, `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`, `STRIPE_PUBLISHABLE_KEY` / `STRIPE_PUB_KEY`, `CHECKOUT_TOKEN_SECRET`, `SITE_URL`, `LOVABLE_API_KEY` (AI gateway), `FIRECRAWL_API_KEY`, `WATI_API_ENDPOINT`, `WATI_ACCESS_TOKEN`, `SENDER_EMAIL`, `GMAIL_APP_PASSWORD`, `SYNC_API_KEY`, `N8N_TOPIC_LEADS_WEBHOOK_URL`, `GOOGLE_ANALYTICS_MEASUREMENT_ID`, `TEMP_BACKFILL_KEY`.

## 2. Business purpose and programmes

Research Platform sells mentored research programmes whose deliverable is a published paper in a peer-reviewed, Google-Scholar-indexed journal. Three catalogue programmes (`_shared/checkout.ts` `PAY_SLUG`/`PRODUCT_NAME`/`APPLY_PATH`):

| Key | Catalogue `pay_slug` | Stripe product name | Apply path | Facts (`_shared/programs.ts`) |
|---|---|---|---|---|
| `research` | `research-publication-fellowship` | "Research Platform \| Research Publication Fellowship" | `/fellowship/apply` | Grades 8-12, 8 weeks, Sundays 9:00-10:30 EDT, $1,199 early bird / $1,799 regular, 12 students per university student mentor |
| `impact` | `global-impact-fellowship` | "Research Platform \| Global Impact Fellowship" | `/impact-fellowship/apply` | Grades 9-12, 16 weeks (paper weeks 1-8 + passion project 9-16), $1,299 / $1,799. Currently "New cohorts coming soon", application buttons disabled (roadmap) |
| `young` | `young-researchers-programme` | "Research Platform \| Young Researchers Programme" | `/young-researchers/apply` | Grades 6-8, 6 weeks, Saturdays 10:00-11:30 EDT, $799 (early 599 per pre-migration doc) |

Other revenue/lead surfaces: an **Australia edition** of the Research Fellowship (`/research-fellowship-aus`, cohort code `ZL-RES-FLAG-240127`, USD 1,199, dedicated portal form since 2026-11-13), the **university Student Mentor Research Masterclass Series** (free Zoom sessions, lead capture → fellowship), the **Global Research Competition** (standalone static page at `/competition`, USD 80 early bird / 100 regular per plan doc), the **Research Interest Questionnaire** (free resource), the **School nomination** flow (schools nominate up to 10 students), free **teacher resources** (worksheets, guides, slide decks), the **Topic Finder** AI tool, the **Ask the Mentors** question form, `/project-10k`, custom programmes for schools, and a 44-post SEO blog. Sales chat ("Luther") captures leads and recommends a programme.

## 5. End-to-end flows

### 5.1 Lead → masterclass → application → payment

1. **Capture**: UTM captured once by `src/lib/utm.ts` (`getStoredUtm`), carried on every URL by `utmCarry.ts`; lead widgets (`components/conversion/*`, `DeferredWidgets`) write `site_leads`; chat writes nothing persistent now; Topic Finder / teacher kit write their lead tables.
2. **Masterclass**: `/masterclass` lists upcoming sessions from `all_masterclasses_public`; `/masterclass/research/apply` posts `submit_masterclass` → `research.submit_public_masterclass_registration` → `public.research_masterclass_regs` (category `research` / `young-research`, `selected_sessions` labels). Confirmation email (`send-application-email` type `masterclass_confirmation`) resolves session rows and injects Zoom join details read server-side.
3. **Apply**: new applicants are redirected to the shared Portal (`portalRedirect.ts`); legacy/native path: form → `submitPublicForm('application')` → `submit_public_application` RPC → `mint-checkout-token` → `goTo('/pay/<token>')`.
4. **Checkout `/pay/:id`** (`pages/pay/PayCheckout.tsx`): `get-stripe-config` → `checkout-context` → (direct mode) `start-direct-checkout` → `create-payment-intent` (+ `validate-promo`) → Stripe Payment Element → `/pay/success` → `payment-outcome`. Price = catalogue early bird or sticker, or the negotiated payment-link amount (promo disabled on links). B2B links collect payer name/email/student count/school and produce one receipt-only row.
5. **Webhook**: `stripe-webhook` verifies signature, finalises on `payment_intent.succeeded` (platform metadata), records refunds. `finalize.ts` matches by `application_id` metadata, else by email (+program_code) — if nothing matches it returns `status: "unmatched"` and logs; there is **no manual-review table** on this platform (unmatched intents are visible only in logs / Stripe). Sibling-programme payments on the shared Stripe account are ignored (`metadataIsSirLuther` / product-name allowlist).
6. **Post-payment**: `triggerEmail('payment_confirmation'|'pending_registration')`, `triggerWhatsApp('payment')`, promo redemption recorded; pay-first payers get a `?complete=<token>&paid=1` link to the native form (`complete-registration`). Reminders: `send-payment-reminders` emails `/pay/<token>` links.
7. **LMS**: not connected here — Research Platform has no learner portal of its own any more (the Learner Portal / `lms` schema is a separate estate app).

### 5.2 Attribution
Application UTMs are frozen at first save (central trigger `tg_default_utm` + `_shared/attribution.ts`); each successful intent appends a payment touch via `record_payment_attribution`; automated emails/WhatsApp carry `lwl-automation` tags; `_shared/utm.ts` registers unknown mediums in the shared `all_utm_mediums` registry.

## 9. Gotchas and lessons

1. **Security hardening is still in progress.** The 2026-11-05 pass added `ssrfGuard.ts`, pinned CDN imports and tightened `role_self_add`; the roadmap's deep scan (2026-11-13) has not reported; nomination and questionnaire endpoints have no visible abuse controls (no `guardPublicAi` on them). Several config.toml `verify_jwt=false` entries reference functions that were deleted in wave 3 — harmless but misleading.
2. **Applications table drift.** Code and AGENTS.md say `public.sirluther_applications` (+ `research.sirluther_applications` mirror). The live central DB (queried 2026-11-24) has neither; only `public.applications` carries `ZL-SIR*` rows (173). The 2026-11-19 Growth Partner Portal retirement audit still listed the table, so it was retired between 11-19 and 11-24. Any function that writes `sirluther_applications` (finalize, start-direct-checkout, complete-registration, reminders, central-db select) must be re-verified against the live DB before trusting it. **Undetermined**: whether a compatibility view was re-created elsewhere (none found in `research`, `public` or `legacy_compat`, which only has `applications`).
3. **Fail-closed RLS**: almost every `research` table has RLS with no policies. Browser code must never query central directly (it cannot — there is no browser client for central). Add new tables with the same expectation and route through `central-db`.
4. **Money is never trusted from the browser**: `loadCatalogue` recomputes; early bird applies only when strictly a discount; payment links are resolved first and a lookup *error* refuses to fall back to list price.
5. **Timing-safe comparisons** (`timingSafeEqual` in `checkout.ts`) are mandatory for tokens, Stripe signatures and service-role bearer checks; HMAC checkout tokens never expire by design (reminders), so secret rotation invalidates all outstanding links.
6. **Prerender invariants**: never put logged-in routes in `PAGES`; keep `.home-compact` scoped; use `goTo` for `/pay`; the competition page is static HTML and must mirror footer/logo manually.
7. **Catalogue is read-only**: cohort/programme facts come from the Console; roadmap blockers are Console corrections (dates/seats), not code.
8. **Masterclass labels**: the pre-migration doc recorded label drift (Grades 8-12 vs 9-12) that broke session matching; sessions now come from the catalogue — never match by free-text label again.
9. **Replication triggers were fire-and-forget** (pg_net, no status read) — the reason the local copies were dropped instead of synced.
10. **Two lockfiles** (bun + npm): keep them in sync or Lovable builds may diverge from local installs.
