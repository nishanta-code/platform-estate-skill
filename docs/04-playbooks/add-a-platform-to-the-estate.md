# Playbook: add a new platform to the shared estate

Distilled from the master architecture doc's "How to change things safely", the Growth Partner Portal build (2026-10-15 → 11-23), the Pre-Med / Pre-Law / Financial Literacy migrations, and the 2026-11-23 hardening. Follow in order; every step has a verification.

## 0. Decide the bucket
- Does the platform need its own `auth.users`? If its users are Group students/staff who already exist, use the shared estate `<ESTATE_REF>` directly (Ops Tool, Application Portal, Pre-Med Platform, Growth Partner Portal, Challenge Platform, LMS do).
- If it is a public marketing site with its own sign-ins and you want blast-radius isolation, use the "own project for auth + estate schema for data" split (Financial Literacy Platform, Pre-Law Platform, Fellowship Platform, Research Platform, Test-Prep Platform, Purpose Platform, Founders Platform).
- Standalone (no Group data at all): own project (Builders Lab, Counselling CRM CRM).

## 1. Assess first — a read-only document
Write an assessment: what tables exist today in the Lovable Cloud project, which are catalogue mirrors (to be dropped in favour of `public.all_*`), which are platform-owned (to be moved), what Stripe account it uses (shared or own), what edge functions exist, what secrets are needed. **Assessment and migration are separate documents** (rule from the Test-Prep Platform incident). Stop and get sign-off.

## 2. Create the schema (additive, in the estate)
```sql
create schema if not exists <platform>;
grant usage on schema <platform> to authenticated, anon, service_role;
-- expose it in Dashboard → Settings → API → Exposed schemas (or it will not be reachable via supabase.schema())
```
- One platform, one schema. Never read/write another platform's schema.
- Add the five restricted catalogue views: `<platform>.all_programs`, `.all_cohorts`, `.all_masterclasses`, `.all_masterclasses_public`, `.all_mentors` (+ `.all_partners` if needed), filtered to the platform's `partner_id` for selling platforms, with `security_invoker = true`, and **no `join_url`/`passcode` column** in any public view. Verify by column list.
- Keep dropped v2 columns as placeholders in the view if legacy code selects them (`'{}'::text[]`, `NULL`, `false`).
- Put `has_role(uid, role)` in the platform schema; pin `search_path = <platform>, public` on every function. Never call `public.has_role()`.

## 3. Tables
- Standard set most platforms end up with: `user_roles` (or `profiles`), `app_settings` (key/value jsonb), `email_templates`, `program_email_settings`, `email_send_log`/`sent_emails`, `whatsapp_templates`/`whatsapp_messages`/`whatsapp_settings`, `captured_leads`/`interest_signups`, `program_map` (platform-side presentation for catalogue rows), `unmatched_payments`, `promo_slot_claims`, `registration_attempts`, `country_dial_codes`.
- Every table: `enable row level security`; explicit policies; **explicit GRANTs to `authenticated`/`anon`** (hand-written migrations get none for free); `created_at`/`updated_at` with a `moddatetime`-style trigger.
- Phone numbers digits-only; prices whole units; no `platform_key` column; reference cohorts by `cohort_id`.
- Do not copy catalogue data locally "for speed". If a field has nowhere to live, say so.

## 4. Clients
- Vite+React: hand-write `src/integrations/<platform>/client.ts` with `createClient(url, anonKey, { db: { schema: '<platform>' }, auth: { storageKey: '<platform>-auth', persistSession: true } })` and a separate `catalog` export on `public`. The LMS's `src/integrations/lms/client.ts` is the model. Leave the Lovable-autogenerated client alone (Lovable regenerates it) but make sure nothing real imports it.
- Own-project split: browser client on the own project; edge functions create `centralAdmin()`/`centralShared(schema)` service-role clients (model: `application-portal/supabase/functions/_shared/db.ts`).
- Secrets: `CENTRAL_SUPABASE_URL`, `CENTRAL_SERVICE_ROLE_KEY` (names vary per repo — follow the repo's `_shared/db.ts`) set via Supabase secrets, never in the repo.

## 5. Registration
Never ship a bare `supabase.auth.signUp()` on the estate. Build `<platform>-register` as an edge function following `docs/01-supabase/auth-and-identity.md` §3: `<platform>.auth_user_id_by_email` RPC (service-role EXECUTE only), `<platform>.registration_attempts` rate limiting, honeypot/min-fill-time, neutral errors, rollback on partial failure. Admin accounts are provisioned by an admin function (`ops-admin-users` shape), never self-service.

## 6. Checkout (build last)
Follow `docs/01-supabase/payments-checkout-and-promo.md`: `/pay/{pay_slug}` page; server-side amount from catalogue (`early_bird_price` > 0 wins else `sticker_price`); central promo validation; `portal.payment_links` read-only via `get_public_payment_link(slug)`; PaymentIntent with `metadata.program_code` (+ application_id, price_id, list_amount_minor, list_currency, identity, school, summary, 3 UTMs); webhook routes on `program_code` first; unmatched → `<platform>.unmatched_payments` + manual review; never auto-match on amount/time; if the Stripe account is shared, keep tolerant matching as a fallback and never remove it until every platform migrated. Add early-bird strike UI only when a real discount exists.

## 7. Edge functions
Deploy with `verify_jwt=false` and in-code auth (estate convention). Name with a platform prefix (`portal-`, `premed-`, `affiliate-`, `ops-`). Use the canonical skeleton in `docs/04-playbooks/edge-function-conventions.md`. Cron jobs call with `x-cron-secret`.

## 8. Catalogue rows
Create the partner row (Console), programmes and cohorts with confirmed prices/dates, mint codes in Console, set `pay_slug`. Never from the platform; never guess. Then the Student Website and Application Portal see it automatically.

## 9. Lovable knowledge + AGENTS.md
Write the platform's rules into its `AGENTS.md` "Project rules" and into Lovable `set_project_knowledge` (≤10 KB, replaces): schema name, never write `public.all_*`, server-side registration, no secrets in repo, link formulas. Point to the two estate master docs.

## 10. Verify (all live, not from files)
- `select * from pg_policies where schemaname='<platform>'` — every table covered.
- `select has_function_privilege('anon','<platform>.auth_user_id_by_email(text)','execute')` — false.
- `supabase migration list --remote` — in sync.
- `get_advisors` security — zero new findings.
- Log in as a real user; create one account through the new register function; run one test payment on Stripe test mode and confirm the webhook row.
- `get_project` on Lovable — `latest_commit_sha` equals what you pushed.
