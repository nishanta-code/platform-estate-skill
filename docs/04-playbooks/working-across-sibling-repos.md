# Playbook: working across the sibling repos without breaking a neighbour

The standing requirement from the owner, repeated verbatim across sessions: **"do not change anything in any other project, do not mix up."** The estate is tended by many agents at once (one Lovable agent per project, plus local sessions). The incidents in `docs/05-lessons/gotchas-and-incidents.md` §B are what happens when that is ignored.

## Rules
1. **One task, one repo.** When asked to use a sibling as a *reference* (e.g. "LMS shell + Website colours for Growth Partner Portal"), copy patterns and values, never files, tables or credentials.
2. **Cross-repo review is read-only** unless the user names the repo to change.
3. **Verify sibling claims independently.** Read the actual client file, query the actual schema, run the actual test. Lovable's own summaries, roadmap.md, and even these docs can be stale.
4. **Which Supabase project does this repo use?** Check the client that is actually imported (`grep -r "from \"@/integrations" src | sort | uniq -c`), not `.env`/`config.toml` alone. The LMS has a dead autogenerated client beside the real one.
5. **Fetch before trust.** `git fetch <remote>` (note: `newrepo` in the Application Portal) immediately before every merge/push and before saying "already fixed"/"still broken".
6. **Never `main` without authorisation.** Default to `feature/<topic>` branches. The user has twice authorised direct merge+deploy for specific work; that approval does not carry over.
7. **Scope-locked forks.** For a multi-repo sweep (the 2026-11-05 pricing fix touched six repos), run one fork per repo with "only touch this directory", "do not run git", "report a diff"; the parent serialises commits. Recon-only forks must be told "do not edit" forcefully.
8. **Cross-schema writes need sign-off.** Growth Partner Portal writing `public.promo_codes` / `portal.payment_links` was a founder-approved exception documented in its `AGENTS.md`.
9. **Lovable knowledge and AGENTS.md travel with the change.** If you harden something, tell Lovable's agent (project knowledge) so it does not revert it.
10. **Update memory/doc corrections in place.** Several architecture claims were wrong for weeks (project ids, "each repo its own project"). Supersede, don't append contradictions.
